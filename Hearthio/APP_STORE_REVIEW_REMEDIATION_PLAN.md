## 1. 执行总原则

必须按照下面的主顺序执行，不因保养闭环开发而跳过前置合规项：

1. **隐私政策**
2. **正式 Bundle ID / 开发团队统一**
3. **通知授权时机调整**
4. **品牌与文案统一**
5. **增强一个真正有差异的保养闭环**
6. **TestFlight 真机验收**

每一步完成后必须由 Reviewer 独立检查。静态检查、单元测试、构建、模拟器、真机和 TestFlight 属于不同证据，不能互相替代。

### 1.1 范围约束

- 先完成最小可提审闭环，不同步扩展账号、云同步、订阅、广告、AI、社区或后台服务。
- 保持离线优先：物品、照片、计划和维护记录默认只保存在本机。
- 不为了“差异化”生成无法证明的设备健康评分、寿命预测或安全结论。
- 旧数据和旧备份必须可迁移；升级失败不得清空现有档案。
- 当前目录不是 Git 仓库。正式实施前必须先建立可恢复的版本基线，或复制一份完整工程快照；未经备份不开始数据模型改造。
- 当前源码集中在 `lib/main.dart`。首轮实现优先做功能最小变更；是否拆文件应以降低回归风险为准，不把大规模重构与提审整改绑定。

## 2. 当前基线与已知风险

### 2.1 已具备能力

- 本地物品建档、搜索、分类和详情展示。
- 购买价、当前估值、保修日期和保养周期记录。
- 多张凭证照片。
- 本地通知。
- 维护记录与费用。
- CSV 导出、ZIP 完整备份和恢复。
- 首页、物品、日程、资产、设置五个主入口。

### 2.2 当前明确问题

- App 内只有简短隐私说明，没有完整、可访问的隐私政策入口。
- Release、Profile 中存在不同 Bundle ID 和开发团队配置。
- 首次进入首页后立即请求通知权限，缺少明确的任务场景。
- 品牌已确定为中文 `家务志`、英文 `Hearthio`，仍需保持 App Store 元数据与 App 内一致。
- 一件物品只能表达一组 `lastCareDate + intervalDays`，无法表达多个具体保养任务。
- 通知不能把用户直接带到对应任务。
- “记录一次保养”缺少执行步骤、耗材、完成结果、照片与下一次计划确认。
- 维护历史没有形成清晰的生命周期时间线和基于事实的统计。

## 7. 阶段五：真正有差异的保养闭环

### 7.1 产品定义与完成标准

产品定位从：

> 家庭物品档案、日期提醒和资产记录工具

收窄为：

> 把每件家庭设备的保养任务变成可计划、可执行、可留证、可复盘、会自动进入下一周期的本地生命周期工具。

首版差异化闭环必须完整演示以下路径：

```text
建立物品
  → 选择或创建具体保养任务
  → 生成下一次计划
  → 首页/日历/通知出现同一任务
  → 点击进入任务执行页
  → 勾选步骤并记录日期、费用、耗材、备注和照片
  → 完成本次保养
  → 明确展示下一次日期并生成新计划
  → 详情时间线保留历史证据
  → 报告汇总真实完成率、逾期和费用
```

以下条件缺一项都不能宣称闭环完成：

- 有明确任务名称，不只是一个周期天数。
- 有可执行步骤或完成内容。
- 有“开始/完成/稍后”动作，不只是静态到期日。
- 完成后生成下一周期，并向用户明确反馈。
- 历史记录与具体计划关联。
- 首页、日历、通知、详情使用同一状态源。

### 任务 CARE-001：建立版本化数据模型和安全迁移

**优先级：P0（闭环内部）**  
**依赖：APP-004**

#### 建议模型

```text
CareItem
  - 现有基础字段
  - List<MaintenancePlan> plans
  - List<MaintenanceRecord> records

MaintenancePlan
  - id
  - title
  - intervalDays
  - reminderLeadDays
  - checklist: List<MaintenanceStep>
  - enabled
  - lastCompletedAt
  - dueDate
  - deferredUntil（仅用于稍后提醒，不改变真实到期日）

MaintenanceStep
  - id
  - title
  - sortOrder

MaintenanceRecord
  - id
  - planId
  - completedAt
  - cost
  - materialName
  - note
  - completedStepIds
  - photos
```

#### 规则

- `effectiveReminderDate = deferredUntil ?? dueDate`。
- 正常完成：`lastCompletedAt = completedAt`，`dueDate = completedAt + intervalDays`，清空 `deferredUntil`。
- “稍后提醒”只设置 `deferredUntil`，不得伪造完成记录或修改原到期日。
- 禁用计划取消对应通知，但保留历史记录。
- 删除计划前必须确认；有历史记录时优先归档而不是物理删除。
- 一件物品允许多个计划，例如“90 天清洗滤网”和“365 天深度清洗”。

#### 迁移策略

- [ ] 新存储使用版本化 envelope，例如 `{schemaVersion: 2, items: [...]}`。
- [ ] 先读取新 key；不存在时读取旧 `care_items` 列表。
- [ ] 旧 `lastCareDate + intervalDays` 迁移成一个“定期保养”计划。
- [ ] 旧 MaintenanceRecord 在无法判断计划时关联到迁移生成的默认计划；若无计划则允许 `planId` 为空并显示为“历史维护”。
- [ ] 只有完整解析、校验和写入新数据成功后，才切换到新 key。
- [ ] 首个稳定版本不删除旧 key，给回滚保留一次机会。
- [ ] 新备份写入 `schemaVersion`；恢复同时兼容旧版和新版。
- [ ] 为 ZIP 恢复增加文件数量、单文件大小、总解压大小和允许路径校验，防止异常备份导致内存或磁盘问题。

#### 验收标准

- [ ] 旧示例数据、旧真实数据、空数据、损坏数据分别有测试。
- [ ] 迁移失败时保留原数据，App 可进入且明确提示，不静默清空。
- [ ] v1 备份可恢复为 v2，v2 备份能完整往返。
- [ ] 多计划、多记录、多照片往返后数据不丢失。

### 任务 CARE-003：待保养任务中心和统一状态机

**优先级：P1**  
**依赖：CARE-002**

#### 状态定义

- `planned`：距离到期超过提醒窗口。
- `dueSoon`：进入提前提醒窗口但未到期。
- `dueToday`：今天到期。
- `overdue`：已过真实到期日且未完成。
- `deferred`：用户设置稍后提醒；仍保留原始到期状态信息。
- `completed`：仅用于历史记录，不作为当前计划的永久状态。
- `disabled`：计划已停用。

所有页面必须调用同一状态计算函数，禁止首页、日历和详情各写一套判断。

#### 实现项

- [ ] 首页增加“待保养”区域，排序为：逾期 → 今日 → 即将到期 → 已计划。
- [ ] 卡片显示物品、任务、原到期日、逾期/剩余天数和主要动作。
- [ ] 提供“开始保养”和“稍后提醒”。
- [ ] 稍后选项：明天、3 天后、下周、自定义；显示原到期日，不能制造“没有逾期”的假象。
- [ ] 日历展示具体任务，不只展示物品。
- [ ] 空状态提供建立首个计划的入口。

#### 验收标准

- [ ] 同一计划在首页、日历、详情显示相同日期和状态。
- [ ] 跨月、闰年、时区变化和当天边界有测试。
- [ ] 稍后提醒不会改变完成率或生成维护记录。

#### 所需证据

- `unit_test`：状态机和日期边界。
- `widget_test`：排序、筛选、空状态和稍后提醒。
- `visual`：逾期、今日、即将到期三种卡片截图。

### 任务 CARE-004：保养执行页与完成事务

**优先级：P1**  
**依赖：CARE-003**

#### 页面内容

- 物品与任务名称。
- 原计划日期及当前状态。
- 准备事项/执行步骤清单。
- 实际完成日期，可修改但需要合理边界。
- 本次费用，必须为非负有限数。
- 耗材名称/型号。
- 备注。
- 保养前后照片，可选。
- “完成本次保养”按钮。

#### 完成事务

完成操作必须作为一个逻辑事务：

1. 校验输入。
2. 生成关联 `planId` 的 MaintenanceRecord。
3. 更新计划 `lastCompletedAt`。
4. 计算并保存新 `dueDate`。
5. 清空 `deferredUntil`。
6. 取消旧通知并安排新通知。
7. 展示明确完成结果和下一次日期。

如果持久化失败，不能只更新 UI；必须提示失败并允许重试。

#### 完成确认示例

```text
本次保养已归档
完成时间：2026 年 8 月 13 日
本次费用：¥129
下一次计划：2027 年 2 月 9 日
提醒：提前 3 天
```

#### 验收标准

- [ ] 未勾完所有步骤时可以提示确认，但不得伪造勾选结果。
- [ ] 完成后记录、计划、首页、日历和通知同时更新。
- [ ] 连续点击不会生成重复记录。
- [ ] 写入或通知失败边界清晰：数据保存成功但通知失败时，记录仍存在并提示通知状态。

#### 所需证据

- `unit_test`：完成事务、下一日期、幂等保护。
- `widget_test`：输入、步骤、照片、确认和错误状态。
- `device`：拍照、相册、保存、通知重新调度。

### 任务 CARE-005：通知携带任务身份并直达执行页

**优先级：P1**  
**依赖：CARE-004、APP-003**

#### 实现项

- [ ] 每条通知使用稳定且低碰撞的 ID，不直接依赖 Dart `hashCode` 作为长期持久身份。
- [ ] payload 至少包含 `itemId`、`planId` 和 payload 版本。
- [ ] 注册前台、后台和冷启动通知点击处理。
- [ ] 点击通知直接打开对应任务详情/执行页。
- [ ] 如果物品或计划已删除，安全回退到待保养列表并显示说明。
- [ ] 编辑计划、禁用计划、完成任务和删除物品时正确取消旧通知。
- [ ] 时区变化或 App 再次启动时重新校正未来本地通知。

#### 验收标准

- [ ] 前台、后台、被终止三种状态点击通知均到达正确任务。
- [ ] 多任务通知不会串到其他物品。
- [ ] 已删除任务不会导致崩溃或空白页。

#### 所需证据

- `unit_test`：payload 编解码和稳定 ID。
- `simulator`：路由逻辑验证。
- `device`：前台、后台、冷启动与时区变化实测；模拟器不能替代最终通知验收。

### 任务 CARE-006：生命周期时间线

**优先级：P1**  
**依赖：CARE-004**

#### 实现项

- [ ] 详情页顶部显示使用时长、累计保养次数、累计费用、下一项任务和当前逾期数。
- [ ] 时间线按日期倒序展示维护记录，并标识对应计划。
- [ ] 每条记录展示完成日期、费用、耗材、备注、步骤完成情况和照片。
- [ ] 支持编辑或删除错误记录；操作后必须重新计算对应计划的上次完成日和下一次日期。
- [ ] 购买/首次安装可作为时间线起点，但必须来自用户填写的数据。

#### 验收标准

- [ ] 多计划记录可区分。
- [ ] 删除最新记录后，计划能回退到上一条有效记录重新计算。
- [ ] 统计值全部能追溯到实际记录，不生成无依据评分。

#### 所需证据

- `unit_test`：累计值、回退重算、排序。
- `widget_test`：空时间线、长文本、多照片和编辑删除。
- `visual`：至少一条完整生命周期样例截图。

### 任务 CARE-007：基于事实的家庭保养报告

**优先级：P2**  
**依赖：CARE-003、CARE-006**

#### 首版指标

- 本月已完成数量。
- 当前逾期数量和累计逾期天数。
- 未来 30 天待处理数量。
- 最近 12 个月维护费用。
- 按物品/类别汇总的实际维护费用。
- 按时完成率，必须在 UI 解释计算口径。

#### 不做

- 无传感器或厂商数据支持的“设备健康分”。
- 无数据依据的剩余寿命预测。
- 把计划费用当成真实支出。

#### 验收标准

- [ ] 每个数字能从测试数据手工复算。
- [ ] 无记录时显示解释性空状态，不展示 100% 等误导结果。
- [ ] 日期范围和完成率口径在页面可见。

#### 所需证据

- `unit_test`：统计聚合和边界数据。
- `visual`：空数据与有数据报告。

### 任务 CARE-008：差异化产品叙事与审核演示路径

**优先级：P1**

#### App Store 叙事

- 截图顺序建议：
  1. 待保养任务中心。
  2. 多计划和模板。
  3. 步骤化执行页。
  4. 完成后自动生成下一次计划。


#### 验收标准

- [ ] 审核员无需登录、联网或外部设备即可走完核心路径。
- [ ] 示例数据明确标注为示例，用户可删除。
- [ ] 截图和描述展示的所有能力都在提审二进制中可用。
